# SQL query compatibility report

## Scope and method

Static search/review of `pool.query` and `conn.query` call sites under `controllers/`, `services/`, and `jobs/`, compared with `rpl_crm.sql`. No SQL executed. No production connection. The source has **112 direct query call sites** (count of API calls, not necessarily one SQL statement per call; loops and dynamic construction can issue repeated executions). Query call sites are summarized by function family below, rather than reproducing interpolated SQL with sensitive values.

## Detailed findings

- No application SQL reference to a missing table or column was found in the reviewed backend call sites.
- `users.email`, `leads.lead_id`, and `lead_contact_phones.phone_number` uniqueness is supported by matching code behavior. Phone uniqueness is global across lead and spouse rows.
- Database status ENUM uses `Lost`; some dashboard conditions compare with `LOST`. The dump collation is `utf8mb4_general_ci`, so case-insensitive comparison is expected, but exact ENUM coercion/writes are not runtime-verified. Keep canonical `Lost` in writes and verify deployed SQL mode.
- `leads` nullable owner FKs align with unassigned leads and transfer/release behavior. `todos.lead_id` and activity actor are nullable as code permits optional associations/actors.
- `lead_contact_phones.is_primary` has no unique/required constraint. Code can create multiple/nonexistent primaries under races or partial failure. `leads.lead_phone` duplicates the primary phone value without a database consistency constraint.
- Phone delete + fallback-primary updates are separate queries; failure can leave the legacy phone value inconsistent.
- Reminder service cancellation and creation have no uniqueness guard or transaction; concurrent updates/jobs may leave multiple active cycles.
- Activity insertion followed by `leads.updated_at` update uses two DB calls; lead state changes also precede activity/reminder calls outside a shared transaction.
- External WhatsApp send occurs before reminder send-count update. A DB failure after delivery can lead to repeated delivery on a later run.
- Lead IDs are generated by selecting latest daily ID then inserting; unique constraint prevents duplicate final IDs but concurrent requests can collide and return an error.
- Team/org dashboard loops issue multiple aggregates per rep (N+1 query growth). Query counts grow with hierarchy size.
- Index concern is workload-dependent: `next_follow_up`, project grouping, activity chronological ordering, and todo done/due sorting have no direct supporting index. `EXPLAIN` and representative volume are required before changes.
- SQL values are generally parameterized. Dynamic lead/todo UPDATE identifiers derive from fixed allowlists; query fragments for scopes are constructed in source from controlled branches.

## Count classification

All 112 call sites are statically compatible at table/column level. **0 confirmed incompatible**, **112 compatible or compatible with caveats**; **attention: 9 issue families** above (race/transaction/value/index/N+1 concerns). The number of distinct expanded SQL statements cannot be reliably equated with call-site count because dynamic statements, loops, and conditional execution vary. No runtime-verification claim is made.
